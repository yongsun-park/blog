## 들어가며

Agent가 PCB 설계를 조회하게 하려면 먼저 PCB 데이터를 정확하게 읽는 프로그램이 필요합니다. 사용자의 질문에 맞는 Net이나 Component, Layer와 관련 정보를 찾아 반환하면 기본적인 기능은 갖춰집니다.

그래서 Agent용 도구도 조회 프로그램을 잘 만들면 된다고 생각하기 쉬워요. 실제로 개발해 보니 그 뒤에 확인할 일이 꽤 많았습니다. **도구가 정확하게 동작하는 것과 Agent가 그 도구를 잘 사용하는 것은 다른 문제**였거든요.

---

## 조회 기능이 정확해도 사용하지 못할 수 있습니다

조회 함수가 정확하고 빠르게 동작해도 Agent가 사용자의 질문에 맞는 도구를 고르지 못하면 답을 만들 수 없습니다. 도구는 맞게 골랐지만 필요한 파라미터를 잘못 구성할 수도 있고, 정상적인 조회 결과를 받아 놓고 다른 의미로 해석할 수도 있어요.

일반적인 프로그램 테스트에서는 입력에 맞는 결과가 나오는지 확인합니다. Agent용 도구는 한 단계 더 봐야 했어요.

- 어떤 질문에서 이 도구를 선택하는가
- 필요한 조건을 파라미터로 제대로 전달하는가
- 반환된 결과를 이해하고 다음 작업으로 이어 가는가
- 확인한 범위 안에서 최종 답변을 만드는가

결국 PCB 조회 엔진의 성능과 Agent의 활용 성능을 따로 확인해야 했습니다.

---

## 도구가 많아지면 인터페이스도 성능의 일부가 됩니다

기능이 적을 때는 Agent가 선택할 수 있는 도구도 단순합니다. 조회할 수 있는 대상과 조건이 늘어나면 비슷한 기능의 도구가 많아지고, 하나의 도구가 받아야 하는 파라미터도 복잡해져요.

이때부터 도구의 이름과 설명, 기능을 나눈 기준이 Agent의 동작에 영향을 줍니다. 하나의 도구에 여러 기능을 넣으면 사용 조건이 복잡해지고, 너무 잘게 나누면 비슷한 도구 중 무엇을 골라야 할지 어려워질 수 있습니다.

반환 결과도 마찬가지예요. 많은 정보를 주는 것이 사람에게는 친절해 보여도, Agent가 핵심을 찾는 데는 방해가 될 수 있습니다. 어떤 정보를 기본으로 주고, 무엇을 다음 조회로 분리할지 실험해야 했어요.

Agent용 도구에서는 **도구 설명과 출력 형식까지 제품 성능에 포함되는 것** 같습니다.

---

## 여러 층의 테스트가 필요했습니다

PCB 조회 도구를 만들면서 테스트도 여러 층으로 나뉘었습니다.

1. **기능·성능 테스트**  
   PCB 데이터에서 기준값을 정확하게 찾는지, 큰 도면에서도 사용할 수 있는 속도로 동작하는지 확인합니다.

2. **Agent 도구 사용 테스트**  
   질문에 맞는 도구를 선택하고 필요한 파라미터를 구성하는지 봅니다.

3. **End-to-End 테스트**  
   사용자의 질문에서 시작해 여러 조회를 거쳐 최종 답변까지 제대로 만드는지 확인합니다.

4. **회귀 테스트**  
   모델과 프롬프트, 도구 설명이나 반환 형식을 바꾼 뒤에도 기존 작업이 유지되는지 다시 확인합니다.

앞의 기능이 통과했다고 뒤의 테스트까지 자동으로 통과하지는 않습니다. 조회 결과는 정확한데 Agent가 도구를 선택하지 못할 수도 있고, 도구 실행은 모두 성공했는데 최종 답변이 질문에서 벗어날 수도 있어요.

---

## 테스트가 도구의 설계를 다시 바꿉니다

테스트는 완성된 도구에 점수를 붙이는 일로 끝나지 않았습니다. Agent가 도구를 잘못 선택하면 이름과 설명을 다시 보고, 결과를 해석하지 못하면 반환 형식과 정보의 양을 조정하게 됩니다.

모델의 성능 문제처럼 보였던 현상이 도구 인터페이스를 바꾸자 해결될 수도 있고, 반대로 도구 설명을 늘렸는데 선택이 더 어려워질 수도 있습니다. 어떤 구성이 좋은지는 실제 Agent에 연결해 반복해서 확인해야 할 것 같아요.

기능 구현과 Agent 테스트가 차례로 한 번씩 끝나는 구조라기보다, 테스트 결과가 다시 도구 설계로 돌아가는 반복에 가깝습니다.

---

## 마무리

Agent용 PCB 조회 도구의 완료 기준을 단순히 “PCB 데이터를 정확하게 조회한다”로 잡기는 어려웠습니다.

Agent가 필요한 순간에 도구를 선택하고, 결과를 이해해 사용자의 질문에 답할 수 있어야 합니다. 그래서 벤치와 성능 실험은 개발이 끝난 뒤 실행하는 검사가 아니라, 도구의 이름과 범위, 출력 형식을 정하는 개발 과정이 되는 것 같아요.

이제는 도구의 기능과 Agent의 활용 성능을 함께 개발해야 하는 것 같습니다.
