## 들어가며

최근 PCB 설계 데이터를 조회하는 Agent의 프롬프트를 조금 수정했어요. Agent가 제가 만든 `coco CLI`를 언제, 어떻게 호출해야 하는지 알려 주는 부분이었습니다.

큰 변경은 아니어서 기존 기능에는 별 영향이 없을 것이라고 생각했어요. 그런데 수정한 버전으로 내부 PCB 벤치를 다시 돌리니, 이전에 통과하던 테스트가 실패했습니다.

---

## 작은 변경이 도구 사용 흐름을 바꿨습니다

사용자가 PCB에 관해 질문하면 Agent는 적절한 `coco CLI` 명령을 고르고, 도면과 조건을 인자로 전달한 뒤 결과를 해석해 답합니다. 이 과정에서 프롬프트는 Agent가 도구를 사용하는 방향을 알려 줘요.

프롬프트를 조금 다듬었을 뿐인데 Agent가 명령을 선택하고 실행하는 흐름이 달라졌습니다. 아직 어느 문장이 실패를 만들었는지까지 정확히 분리한 것은 아니에요. 다만 변경 전에는 통과했고 변경 뒤에는 실패했다는 사실은 벤치가 바로 보여 줬습니다.

만약 테스트가 없었다면 기능이 깨졌다는 사실을 사용자가 질문한 뒤에야 알았을 수도 있어요. 답변이 자연스럽게 보였다면 오류를 더 늦게 발견했을지도 모르고요.

---

## AI 제품의 품질은 여러 요소의 조합입니다

AI 솔루션의 품질을 이야기할 때 모델 성능을 먼저 봅니다. 물론 모델이 중요하지만 실제 제품에서는 모델만 움직이지 않아요. 프롬프트와 Tool 설명, 실행 환경, CLI 버전이 함께 동작합니다.

이 중 하나만 달라져도 결과가 바뀔 수 있어요. 같은 모델에서도 프롬프트 변경으로 기존 기능이 깨질 수 있고, 성능이 더 좋아진 새 모델로 교체했는데 특정 업무에서는 전에 하던 방법을 놓칠 수도 있습니다. 모델과 관련 기술이 빠르게 바뀌는 만큼, 잘되던 기능을 계속 잘되게 유지하는 일도 생각보다 어렵습니다.

일반 소프트웨어도 기능을 수정한 뒤 기존 기능이 깨지지 않았는지 회귀 테스트를 합니다. AI 제품에는 모델의 판단과 도구 선택 과정이 더해지기 때문에 확인해야 할 범위가 더 넓어지는 것 같아요.

---

## 실제 업무가 내부 테스트 케이스가 됩니다

PCB 설계 조회 기능을 검사하려면 최종 문장이 그럴듯한지만 봐서는 부족합니다.

- 질문에 맞는 명령을 선택했는지
- 올바른 도면과 조건을 전달했는지
- 조회한 Net·Component·Layer가 맞는지
- 반환한 수치와 대상 객체가 기준값과 일치하는지
- 도구 실행이 실패했는데도 답을 만들어 내지는 않았는지

이런 항목을 함께 봐야 해요. 실제 사용자 질문과 자주 발생하는 실패를 테스트 케이스로 남겨 두면 프롬프트, 모델, Tool 설명이나 CLI를 바꿀 때마다 같은 조건으로 다시 확인할 수 있습니다.

실패한 사례도 중요한 자산이 됩니다. 이번처럼 변경 뒤 깨진 작업을 테스트에 남기면 다음 수정에서 같은 문제가 다시 생기는지 바로 확인할 수 있으니까요.

---

## 마무리

벤치마크라고 하면 모델 순위를 정하는 시험부터 떠올리기 쉽습니다. 제품을 만드는 입장에서 내부 벤치는 **어제 되던 기능이 오늘도 되는지 확인하는 장치**에 더 가까워요.

모델의 성능은 계속 올라가지만, 내가 만든 AI 솔루션의 품질까지 자동으로 올라가는 것은 아닙니다. 기술 변화가 빠를수록 실제 업무를 담은 내부 테스트 케이스와 회귀 테스트가 더 중요한 제품 자산이 될 것 같아요.
